                    Separación en proyectos

En gRPC ambos roles/proyectos deben tener la deﬁnición de los servicios (el
.proto) y generar el código del servicio a partir de esa deﬁnición.
Sobre esto cada uno genera su código particular

===== PAGINA 6 =====

                        Plugin Maven Assembly

La ejecución con el plugin spring-boot:run es aceptable para el
desarrollo pero en caso de que deseemos distribuir nuestra aplicación es
mejor generar un comprimido con todo lo necesario.
El proyecto cuenta con el plugin maven-assembly, que permite empaquetar
proyectos con sus dependencias en un tar.gz.
A medida que se va generando el código para el proyecto se ejecuta:
$> ./mvnw clean package
para construir el proyecto, correr tests y empaquetar.
Genera un archivo tar.gz con las clases y jars de dependencias listo para
usar, uno por cada proyecto.

===== PAGINA 8 =====

                      Plugin Maven Assembly

Para ejecutar los proyectos server y client
1. Entrar en la carpeta target de cada proyecto
2. Descomprimir los *-bin.tar.gz (usando tar -xzf <path>)
3. Entrar en la carpeta que aparece y dar permisos de ejecución a los
   scripts run-*.sh (chmod u+x <path>)
4. Revisar dentro de los scripts que el Fully Qualiﬁed Name de la clase a
   ejecutar sea el correcto
5. Una vez hechos estos pasos, se puede ejecutar en 2 consolas
   diferentes

                                  Docker
Otra forma de ejecutar el proyecto es utilizando Docker. Para ello se generará
un contenedor para el servidor y un contenedor para el cliente con la
particularidad de que este último se crea y se destruye.
Tanto en server como en client, se encuentra un archivo Dockerfile con
las instrucciones para construir la imagen que se ejecutará en el contenedor.
            FROM amazoncorretto:25-alpine-jdk
            WORKDIR /app
            RUN apk add <-no-cache bash
            COPY target/grpc-greeter-server-2026.1Q-bin.tar.gz .
            RUN tar -xzf grpc-greeter-server-2026.1Q-bin.tar.gz \
               <& rm grpc-greeter-server-2026.1Q-bin.tar.gz \
               <& chmod +x grpc-greeter-server-2026.1Q/run-server.sh
            WORKDIR /app/grpc-greeter-server-2026.1Q
            EXPOSE 50051
            ENTRYPOINT ["bash", "run-server.sh"]

===== PAGINA 15 =====

                         gRPC - Deadlines - Client
➢ Un cliente puede deﬁnir un deadline (timeout) que indica hasta cuándo está
  dispuesto a esperar.
➢ Por defecto gRPC no deﬁne un deadline por lo que un cliente podría quedarse
  esperando una respuesta para siempre.
➢ Si se vence el plazo, el cliente aborta y se obtiene DEADLINE_EXCEEDED
   try {
      var response = greeterBlockingStub
              .withDeadlineAfter(5, TimeUnit.SECONDS)
              .sayHello(request);
      log.info("Greeting: {}", response.getMessage());
   } catch (StatusRuntimeException ex) {
      log.error(ex.getMessage());
   }                                 DEADLINE_EXCEEDED: CallOptions deadline exceeded after
                                        4.989594083s. Name resolution delay 0.004798625 seconds.




    Deadlines | gRPC

===== PAGINA 16 =====

                     gRPC - Deadlines - Server
➢ Para evitar desperdiciar recursos gRPC cancela automáticamente la
  ejecución del método cuando el plazo se vence y gracias a eso se obtiene
  CANCELLED en el cliente.
➢ Pero esa cancelación no detiene por sí sola el procesamiento interno de la
  aplicación. Si se dispararon tareas para atender esa invocación, se puede
  veriﬁcar periódicamente si la llamada fue cancelada y así ﬁnalizar el
  procesamiento
    if (Context.current().isCancelled()) {
       responseObserver.onError(<<.);
       return;
    }

public class HealthConfig {

       var healthStatusManager = new HealthStatusManager();
       healthStatusManager.setStatus(GreeterGrpc.SERVICE_NAME,
                                       HealthCheckResponse.ServingStatus.SERVING);
       return healthStatusManager;
    }

}

===== PAGINA 22 =====

                      Protocol Buffers
message User {
 int32 id = 1;
 string user_name = 2;
 string display_name = 3;
 AccountStatus status = 4;
 repeated string preferences = 5;
}

➢ Las estructuras pueden ser message o service
➢ Los tipos pueden ser
   ○ Scalar Value: double, ﬂoat, int32, uint64, bool, string, etc.
   ○ Enumerations
   ○ Otros message ya deﬁnidos (composición)
➢ Es obligatorio asignar a cada campo un número único entre todos
  los campos de ese mensaje

===== PAGINA 23 =====

                       Protocol Buffers
➢ En cuanto a la cardinalidad existen los modiﬁcadores:
   ○ optional: Ese campo tendrá dos estados posibles, seteado y
      contiene un valor que será serializado o “unset” de forma que
      retorna el valor por defecto y no será serializado
   ○ repeated: El campo se repite 0 o más veces y se preserva el
      orden (lista)
   ○ map: Una colección de pares clave/valor
➢ Se permiten Nested Types
➢ Los comentarios soportados son:        message UserRoles {
                                           map<string, Role> roles_by_site = 1;
   ○ // Comentario Inline                }
   ○ /* Comentario
            Multiline */

===== PAGINA 24 =====

                    Protocol Buffer - Enum
Protobuf permite usar enum como tipo para deﬁnir uno con un número ﬁnito
de posibles valores

                      enum AccountStatus {
                       ACCOUNT_STATUS_UNSPECIFIED = 0;
                       ACCOUNT_STATUS_PENDING = 1;
                       ACCOUNT_STATUS_ACTIVE = 2;
                       ACCOUNT_STATUS_SUSPENDED = 3;
                       ACCOUNT_STATUS_CLOSED = 4;
                      }




Los valores deben contar con el preﬁjo del enum (ACCOUNT_STATUS_…)
y es necesario declarar un default value llamado …_UNSPECIFIED con 0
como valor numérico

===== PAGINA 26 =====

                            gRPC - Wrappers
Para no estar creando mensajes vacíos o simples que cuentan con un solo
tipo escalar se provee una biblioteca de mensajes wrappers:
➢   google/protobuf/wrappers.proto
➢   google/protobuf/empty.proto
       message StringValue {
        // The string value.            message Empty {}
        string value = 1;
       }

Para usarlos basta con incluir la sentencia import correspondiente:
import "google/protobuf/wrappers.proto";
import "google/protobuf/empty.proto";
service PingService {
 rpc Ping(google.protobuf.Empty) returns (google.protobuf.StringValue);
}

===== PAGINA 29 =====

                gRPC - Llamados Asincrónicos
Para situaciones donde queremos utilizar llamados no bloqueantes
gRPC provee dos estrategias de llamados asincrónicos:
➢ Resolución por Future
➢ Resolución por StreamObserver / Callback
De esta manera podemos aprovechar las ventajas de realizar llamados
asincrónicos y liberar los recursos del sistema mientras el servidor
procesa el pedido.
En principio para usar llamadas asincrónicas el código en el servidor
no varía, si cambia el cliente.

===== PAGINA 30 =====

                          gRPC - FutureStub
El cliente instancia un nuevo stub llamado *FutureStub a partir del método
newFutureStub del código generado
 @Bean
 UserServiceGrpc.UserServiceFutureStub userFutureStub(GrpcChannelFactory channels) {
    return UserServiceGrpc.newFutureStub(channels.createChannel("local"));
 }

===== PAGINA 31 =====

                         gRPC - FutureStub
Al realizar un llamado a los métodos remotos del FutureStub el mismo retorna un
ListenableFuture
 public interface ListenableFuture<V extends @Nullable Object>
                                                    extends Future<V> {
  void addListener(Runnable listener, Executor executor);
 }

Por lo que permite acceder a la respuesta de dos maneras:
➢ Utilizando la funcionalidad de la interfaz Future
➢ Agregando un callback

 Futures.addCallback(userFuture, userCallback, executorService);

===== PAGINA 32 =====

                        gRPC - FutureStub
El callback es un FutureCallback que provee un método para el caso de
error y otro para el success.
  static class UserCallback implements FutureCallback<User> {
     private static final Logger logger =
                        LoggerFactory.getLogger(UserCallback.class);

      @Override
      public void onSuccess(User user) {
          logger.info("received user {}", user);
      }

      @Override
      public void onFailure(Throwable throwable) {
          logger.error("reaching for user", throwable);
      }
  }
